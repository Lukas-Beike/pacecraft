# Continuous integration and releases

- **Gitar Reviews**: The installed Gitar GitHub App provides the required `Gitar` check for the current PR head. An isolated ruleset requires this context from `gitar-bot` (integration ID `827041`) on `develop` and `main`; Dependabot and the release app are exempt from that ruleset. Default and Main release protection separately require their CI checks and all review conversations to be resolved, including outdated threads. The release app is not exempt from either of those rulesets. Each ruleset also has an existing user-level pull-request bypass. Fix or reconcile findings before resolving threads. Ordinary PR comments have no resolved state: complete their requested action or record an evidence-based disposition before merging. Hosted automatic review settings are managed in Gitar; disable the former automatic Codex review in [Codex Settings](https://chatgpt.com/codex/settings/code-review) if it is still enabled. Local review remains optional additional evidence.
- **Dependency Updates**: Dependabot updates pip, npm, Docker and GitHub Actions on `develop`, offering a new version only after a 3-day cooldown so a compromised release has time to be pulled. Squash auto-merge is enabled for patch, minor and major updates; protected-branch checks and review-thread resolution still apply. The privileged auto-merge workflow never checks out or executes PR code. Dependabot runs receive no secrets, so after each push to `develop` and every 10 minutes the auto-rebase workflow uses the trusted `develop` copy of `tools/quality_baseline.py --align-versions` to read open Dependabot PR files as data and commits only the aligned tool-version record through the GitHub App, rejecting the commit if the PR head moved after the reads. The same workflow rebases (never merges) same-repository PRs with squash auto-merge onto `develop` one at a time, in the order auto-merge was enabled: none while one is up to date and its checks still run, otherwise the first behind PR whose checks finished green, so a busy `develop` no longer restarts every armed PR's browser shards (#3979). It runs after each push, after each finished CI run and every 10 minutes, which also covers a PR armed after the last push (#3854); a check pending for 3 hours no longer holds the queue.
- **Automated Daily Releases**: At 03:00 UTC, an automated workflow inspects `develop`. If new commits exist and no open issue or PR carries the `release-blocker` label, it creates a version-bump PR and a promotion PR to protected `main`. Both branches require their configured test, quality and browser checks; the release app cannot bypass those requirements. After successful main tests, the workflow creates an immutable GitHub release and publishes the container: the promotion PR, the main push and the release run reuse the native, browser and quality results of the version commit's develop push when the tree is identical (they still build the image and run the container tests), and the release run pushes the exact `pacecraft:ci` image it built, container-tested and described in the SBOM (on a reused tree its browser evidence comes from the reused run's build of the same tree) (no rebuild) and attaches that SBOM as a signed attestation. The container digest is signed and verified before promoting `latest`; the version tag and `latest` must resolve to that same digest. While any `release-blocker` item is open, the scheduled run skips the bump and promotion and names the blockers in its job summary; if that label query fails, the run fails without releasing. Add the label to the blocking fix's issue or PR and remove it (or close the item) to resume. Manual dispatch is not gated. A read-only release preflight also verifies `APP_VERSION` before its tag exists. Actions use read-only default permissions, with explicit job-level write permissions where needed.
- **Release Changelog in the Image**: Before the image job builds `pacecraft:ci`, it checks out the full history with tags and runs `scripts/release_changelog.py`, which writes `public/changelog.json` from local git only: per release tag the German `Changelog:` commit trailer of each commit since the previous release (commits without the trailer are not listed), newest first, plus a first section for an unreleased build's own commits. A tag whose tree is not in the history is skipped with a build warning; if the build's own range cannot be computed, the job fails. The app reads the file from its own server and never asks GitHub; local builds have no file and show only the version. Two builds of the same tree can differ only in this file (the develop push of a version commit has an unreleased section, the release build none); the browser runner's image-to-checkout comparison leaves it out, and reused browser evidence covers the same application code.
- **GitHub Pages**: The project site in `site/` deploys only from `main` (or a manual dispatch), so unreleased site changes on `develop` stay private until the release; the `github-pages` environment allows only `main`.
- **Run cancellation**: A newer push to the same PR cancels that PR's older test-and-publish run, and a newer `develop` push cancels the older `develop` push run. The release version commit's `develop` run, `main` push, release and dispatch runs always finish. The promotion reuses the run of the `develop` tip it was cut from; when that is a later commit whose run was cancelled, the promotion runs the full suite.
