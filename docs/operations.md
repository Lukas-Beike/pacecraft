# Operations, backups and diagnostics

## SQLCipher Encryption
All persistent application state is stored in `/data/intervals-coach.db` encrypted with AES-256 via SQLCipher. The database key is derived from `APP_PASSWORD`. The application will refuse to start without SQLCipher libraries present.

If `APP_PASSWORD` does not open the existing database, each start attempt stops with one critical log entry (`secure_startup_refused`, reason `database_unreadable`) and the message "Die Datenbank lässt sich mit diesem App-Passwort nicht öffnen: Das Passwort passt nicht, oder die Datei ist beschädigt. Die Datenbank wurde nicht verändert." and exits non-zero; with `--restart unless-stopped` Docker repeats the attempt. Set `APP_PASSWORD` back to the value the database was created with; the database is not modified. SQLCipher reports a damaged first page the same way, so if the password is certainly right, restore from a backup (#2912).

Each pooled database connection uses a 16 MiB page-cache budget to reduce repeated encrypted reads of large histories. The default pool has four readers and one writer (up to 80 MiB of page caches, allocated as needed). Two readers were faster on a synthetic history (#2788) but starved views on a long production history, where requests hold a read for seconds (#2965). `runtime.reader_slots` in the diagnostics counts the waits for a reader. The view reads over the history (performance, power profiles, training records, context preview, trends and the week review) run one at a time before they take a reader and leave the gate before their response is sent; the activity list is a bounded page and does not wait (#3125); a read waits at most 5 s and then runs anyway, `runtime.heavy_read_gate` counts those waits, and a route's time in `runtime.slowest_routes` includes its wait (#3029). `runtime.slowest_routes` lists the slowest API routes since start by route pattern (no ids or queries): count, median (p50), p95 and maximum milliseconds to the response status, and client disconnects, and `scripts/prod_diagnostics.py --section route_timings` prints them (#3630); every `http_access` log line carries `status` and `duration_ms` (#3017). `runtime.session_reports` counts the Coach's session reports built since start, their checks by verdict and how session references resolved (by ID, by date, newest, ambiguous, not found), counts only (#3084). Every session's summary, which the equipment section and each activity detail need, is kept in memory until a commit changes rows. So is the 12-week energy history ending yesterday that Verlauf's period balance reads for its own day totals: it prices every session from its streams, and repeating it on each Verlauf read slowed the views that load right after it (#3630).

## Maintenance Mode & Database Restoration
When a database restore is initiated:
1. The uploaded backup is first written in 1 MiB chunks to a new staging file in `/data`, so it is never held in memory as a whole; the size limit is enforced while writing. Staging does not touch the live database, and the staging file is removed when the restore ends. If the process is killed first, leftover staging files, unencrypted privacy-export archives and database-backup snapshots stay in `/data` until the next start removes them before any worker runs.
2. The application enters an exclusive maintenance mode, rejecting new incoming API mutations with an HTTP 503 maintenance notice.
3. A running Coach answer is cancelled first, like a chat reset (the local data purge and the GPS-track deletion do the same); active background sync jobs are allowed to finish. The wait is bounded at 20 seconds: if work is still running by then, nothing is changed and the request returns HTTP 409 with a retry hint.
4. If an active database exists, a timestamped pre-restore copy is saved beside it in `/data` using the name `intervals-coach.db.pre-restore-<timestamp>-<id>`. The restore is refused with HTTP 507 when `/data` lacks the free space for this copy, and a partial copy is deleted. Once the restore has completed and this copy is verified (same size as the database it copied, opens with the key, current schema, passes an integrity check), the older pre-restore copies are deleted so that only the newest remains; a failed restore, an unverified copy or a copy taken while the live database still had unflushed write-ahead-log frames keeps them all.
5. The replacement database must have the current schema (version 34), version 33 (since 2.1.51), version 32 (since 2.1.28), version 31 (since 2.1.22), version 30 (since 2.1.20), version 29 (since 2.1.17), version 28 (since 2.1.10), version 27 (since 2.1.2) or the oldest supported schema (version 26, release 2.0.5; the releases of each schema are in [schema-history.md](schema-history.md)), which are upgraded in place; older, newer or unknown schemas are rejected unchanged (a backup from before release 2.0.5 is refused with a message naming that release; open it with release 2.0.5 first and back it up again). It must also pass SQLite integrity and foreign-key checks. Restored sessions are cleared before it is installed; failed validation rolls back the staged changes.
6. If valid, the new database is swapped into place and the maintenance gate is lifted; if invalid, the original database is preserved without data loss. A storage failure during the copy or swap returns HTTP 507 (disk full) or 500 instead of a validation error and leaves the original database and its WAL files in place.

The limits are fixed values, not settings: a database backup or restore upload of at most 1 GB (1,000,000,000 bytes), a privacy export of at most 100 MB, 120 seconds to prepare a download and 10 MB of free space kept in `/data`. A database above 1 GB can be neither backed up nor restored through the app; back it up by stopping the container and copying the `/data` volume.

## Idempotency Store for the Offline Outbox

The four routes the device outbox may send again (`POST /api/nutrition/entry`, `PUT /api/body/weight`, `PUT /api/body/body-fat`, `POST /api/activities/{id}/feedback`) accept an `Idempotency-Key` header with a UUID. The HTTP layer keeps the first 2xx JSON answer in the key/value table under `idempotency:<uuid>` with its path for 30 days (included in backups and the privacy export, deleted by the local data purge); a repeated key on the same path answers it without writing, the same key on another path answers 409, and older entries are deleted whenever a result is stored. For a meal and a session feedback the handler runs in one transaction that also keeps the answer, and the answer is sent only after that commit, so a crash leaves both the write and its key or neither: they are written exactly once. A weight or body fat save is followed by its Garmin push in the same request, which must not hold the single writer during a network call, so its answer is kept after its own commit; a crash in that short window lets a replay set the same day's value again (one value per day, never a second entry).

## Privacy Export & Data Purge
- **Full Privacy Export**: Download a single comprehensive ZIP archive of JSON and JSON Lines files containing all stored profile fields, workouts, check-ins, activity notes, and chat history. Export format version 24 also includes the canonical provider tables (provider records, activity sessions with the survivor each deleted merged session keeps, activity records, observations), the canonical activity detail (detail sets, stream channels as decoded point lists with `null` gaps, laps, zone times, strength sets and session analyses) and the canonical sleep periods, zone configurations with decoded limit lists, provider statuses, gear and gear-to-activity links, retired rows included, as JSON Lines, the owning provider and session of each activity note, when known, and the remote links that map local workouts, planned units and competitions to their provider counterparts (including the provider of each competition sync tombstone). Stored sports are exported in the canonical vocabulary (`sport`, `environment` and a lossless `sport_detail`), and planning records name their start and planned duration `starts_at_local` and `planned_duration_s` (since version 8); version 9 adds the canonical power curve, version 10 the session RPE rating time of each activity note, version 11 the lifecycle (`state`, `owner_record_id`) of each observation, version 12 the executed strength sets with the source of each set list, version 13 the athlete's marking of what a session was, version 14 the stored non-secret provider fields, version 15 the heart-rate and power source and the named sensors of each stream set, version 16 its stored first threshold estimate, and version 17 the sync bookkeeping of workout-library entries, the creation and sync times of training snapshots and the creation and update times of competitions (workout-library and snapshot lines now hold one object per row with the stored document under `payload`) plus the Coach approval proposals without their session and action-token hashes, version 18 the foods saved from database lookups as rows of the product file with their origin and fetch time instead of a separate file, version 19 the athlete's training impact per calendar event (`external_calendar_decisions.jsonl`, UID and occurrence start without event text), version 20 the location of each competition, version 21 the watch workout data of laps and detail sets (the workout step, trigger, breathing rate and grade-adjusted speed of each lap, the workout steps of a lap set and the zone basis of a stream set), and version 22 the drink volume (`volume_ml`) and the session (`session_id`) of each diary entry, with the meal types `pre_session` and `during_session`, version 23 the portion and package size (`portion_amount`, `portion_unit`, `package_amount`, `package_unit`) of each product, and version 24 the athlete's feel after a session (`feel`, 1 very strong to 5 very weak) of each activity note; credential-like keys are removed from provider payloads before export, and signed download URLs are replaced with a `[redacted]` marker.
- **GPS tracks**: Position channels (`latitude_deg`, `longitude_deg`) of Garmin and Wahoo FIT files are stored as stream channels in the encrypted database and are part of the backup and the privacy export. They are never merged into read models, so the Coach, the activity detail API, diagnostics and logs never see raw coordinates. The switch "GPS-Spuren speichern" (**Mehr** → privacy section, `GET`/`POST /api/privacy/gps`, default on) stops storing positions of newly fetched files; stored tracks stay until the athlete confirms `GPS-SPUREN LÖSCHEN` (`POST /api/privacy/gps/delete`). Turning the switch on again stores positions only for files fetched from then on. The local data purge deletes them with the stream channels and keeps a switched-off switch off. Repeated routes derived from the tracks (`activity_routes` and `activity_routes_state` in the key/value store, written by the canonical backfill stage `activity_routes`) are deleted in the same request when the stored tracks are deleted, including the athlete's route names, and are not rebuilt without tracks (turning the switch off alone keeps them); the Coach and the activity view get only a route label, visit count and the visits' own session values, never a position.
- **Local Data Purge**: Completely wipes all local athlete records from the database, including canonical provider data, and deletes the recovery copies of the database that restores and the Intervals.icu purge of release 2.0.0 (its code is removed; its copies stay on disk) saved beside it, together with the purge marker file, and, as its last step, the server log files (rotations removed, the active file emptied). The confirmation dialog lists them (count only) before anything is deleted; a copy or log file that cannot be removed is reported. To prevent accidental loss, the action requires entering the exact confirmation phrase `LOKALE DATEN LÖSCHEN`. External accounts (Intervals.icu, Garmin and Wahoo) remain untouched, except that the app's Wahoo grant is revoked at Wahoo before the tokens are wiped (best effort; a failed revoke is reported in the receipt and the purge completes). The purge and the GPS-track deletion overwrite the deleted content with zeros, then truncate the write-ahead log and run `VACUUM` under the maintenance gate, so the old data no longer remains in the database file or the log; this takes extra time and needs temporary free disk space of about the database size. A failing reclaim is logged (`privacy_space_reclaim_failed`) and leaves the committed deletion and all data intact. The write-ahead log is also truncated every few minutes when idle (`wal_checkpoint_failed` on failure) and limited to 64 MiB after a checkpoint.
- **What OpenAI keeps**: Coach requests are sent with `store: false`, so OpenAI keeps no response object, and tool rounds of one turn continue statelessly: the next request resends the turn's items (tool calls, their outputs and the model's reasoning as `reasoning.encrypted_content`) instead of a `previous_response_id`. One path stays stored because the API needs it: the conversation that follows an image or file upload. OpenAI keeps those responses for its own retention period; the local data purge deletes the conversation at OpenAI (reported separately if that fails) but cannot delete single stored responses. Attachments reach OpenAI as measurements only; see [Coach](coach.md#multimodal-capabilities).

## Operational Logging & Diagnostics
- **Sync Job History and Retry Cadence**: The automatic schedule (hourly; Garmin with a Personal API key after its change check, see [synchronization](synchronization.md)) follows `provider_refresh_history.next_retry_at` (exponential, at most 6 hours, never earlier than a provider-named `Retry-After`); a refresh that failed with `auth_required` is not retried automatically until the athlete acts (manual refresh, restart or changed credentials). `garmin_sdk_required` is final and not retried. While a provider's full resync runs, its queued jobs stay queued (no attempt is consumed) and a rejected operation is recorded as `skipped`, not `error`. A refresh that meets a running read of the same provider (lock contention) is likewise recorded as `skipped`; a skipped row is neither a success nor the latest attempt for the freshness strip, and it neither ends nor extends a failure streak or retry hold. A queued refresh job that meets such a read is requeued after 30 seconds without consuming an attempt (after 30 minutes of contention it fails and retries on the normal backoff), and the Coach's waiting Wahoo refresh waits on the lock itself for up to two minutes. Completed `sync_jobs` (with their items) are pruned from the hourly maintenance once they are older than 30 days, always keeping the newest 200 jobs; queued, running, failed and partial jobs are never pruned. A backfill chain (history, wellness, streams) runs the derived passes (local load, canonical backfill, Wahoo metric export) once when its last batch ends, and a Coach refresh that waited or a full resync requests them when it finishes. A backfill chain that stopped before its history floor (a job that used up its retries, a partial chunk, or a provider connected while the app runs) is queued again by the periodic schedule, at most once every 6 hours per chain, and at once when Wahoo or Garmin is connected; a file or record skipped after three failed runs no longer fails the job. A job whose outcome could not be stored no longer stays `running` until a restart: before its next claim the worker requeues a read-only job (refresh, activity details, backfills; failed after three attempts), while a job that may have written to a provider (plan, competition or nutrition push) is marked `failed` with `outcome_not_persisted` and runs again only when the athlete resolves it; a restart or a database restore applies the same rule to jobs it finds `running`, and the three-attempt bound carries across restarts. A provider refresh a stopped process left `running` is closed by the restart or restore as `skipped` (phase `interrupted`, error code `process_interrupted`), so the freshness strip shows the last real outcome instead of a lasting "syncing". The same start-up step ends a full resync or a Garmin data operation left running, and offers workout-library and planned units left `syncing` again as push errors ("Die Übertragung wurde unterbrochen."), on a restored database as well (#2888).
- **Sanitized Logs**: Standard container logs contain only operational timestamps, correlation IDs, status codes, and anonymized error classifications. API tokens, passwords, and athlete metrics are never logged.
- **Always-on Technical Diagnostics**: The application keeps up to 10,000 diagnostic entries from the last 7 days (2 MiB total, 512 KiB per entry, with truncation marked), covering tool activity and classified provider error details such as status, error code and request ID. Responses of every service and request bodies of Garmin, Wahoo, Intervals.icu and other non-OpenAI services are stored only as a shape (field names, types, lengths), never as values. Request bodies sent to OpenAI are stored sanitized and can contain the Coach's dialogue and training context. Raw OpenAI or Anthropic error text is not stored. Credentials, keys, tokens, and session data are removed before storage. The stored list is rewritten at most every 30 seconds.
- **Server Log Management**: In **Betrieb & Diagnose**, authenticated users can download the sanitized current server log and its available rotations as JSON Lines, or delete the log files. The server keeps ten log files of up to 5 MB each (the current file plus nine rotations). Routine polls (chat, sync, job, health and auth status, and the state event stream) and per-activity backfill calls are logged at DEBUG and not kept; failures stay at INFO or above. The diagnostic report includes the latest 200 warnings and errors and the latest 100 INFO lines across all rotations.
- **Diagnostics Management**: In **Betrieb & Diagnose**, authenticated users can download the sanitized technical diagnostic report as JSON, or clear the stored technical diagnostic entries.
- **Canonical Coverage Summary**: The diagnostic report includes a `canonical_coverage` section with per-provider counts only: activities, observations, issue counts per reason, and whether a sync time is stored. Garmin and Wahoo report the stored totals of the canonical tables; the counts of Wahoo's last fetch alone are under `last_fetch`, because a fetch window changes them. It contains no dates or record content. If the summary cannot be computed, the section reports `unavailable` without details.
- **Report Sections**: Every section of the diagnostic report is built on its own, so one failing section reports `{"status": "unavailable"}` and the endpoint still answers. `database.schema_version` names the database schema, `configuration.openai_base_url_custom` says only whether a non-default OpenAI endpoint is set, and the `wahoo` block shows `configured`, `connected`, `scope`, the access-token state (`valid`, `expired`, `unknown`), `last_wahoo_sync_at` and the redacted `last_wahoo_sync_error`, never tokens or expiry times. Yazio, Open Food Facts and Wahoo FIT requests are logged and captured with host, status and error class only.
- **Canonical Backfill Status**: The diagnostic report includes a `canonical_backfill` section next to `canonical_coverage`. Providers write their canonical rows live; the backfill only re-projects them. Active provider records whose mapper version is behind the current version are re-projected from their stored raw data, in batches. Re-projection never revives a deleted activity, and leaves an activity whose session is deleted untouched. When the new projection no longer emits an activity that an active raw record owns, that activity becomes `invalid` (its session keeps its state) and is counted as `retired`; a later mapper version that emits it again makes it `active` with the same id, counted as `reprojected`. Observations are not retired: an observation that an upgraded mapper no longer emits keeps its old `mapper_version`. While a re-projection is pending, the table reader serves each observation at the newest version stored for it, so nothing disappears; once the backfill completes it serves only observations at the current version. A mapper-version change during a partial re-projection restarts the re-projection scan, including records already passed by the interrupted run. Rows of a provider without a mapper, such as Intervals.icu rows of a database restored from a release before 2.0.0, are left as they are; this build contains no code that deletes them. Temporary writer contention waits and retries the same batch. The section reports `status` (`pending`, `running`, `complete`, or `failed`), the number of `batches`, and per-provider counters: `skipped_invalid`, `duplicates`, `reprojected`, `retired`, and `added` (observations a re-projection writes for a natural key that had no stored row, the days a mapper change newly fills). It contains counts only, never activity ids, names, or dates. A raw record whose mapper raises is counted as `skipped_invalid`, keeps its mapper version and existing canonical rows and does not stop the pass; the log line names only the error class. Once the pass completes, the reader serves only observations of the current mapper version, so the observations of such a record stay stored but hidden until a later mapper version projects it; its activity rows stay served. A `failed` canonical run retries from its saved cursor after a delay; follow-up stages resume on the next pass. If the status cannot be read, the section reports `unavailable`. `scripts/prod_diagnostics.py --section canonical_backfill` prints the status, `batches` and those per-provider counters, so a post-release check after a mapper bump can tell whether the re-projection pass is done (#3595). Activity details are served only from the canonical tables as `activity_detail.v1` for every provider.
- **LT1 Ride Coverage**: The diagnostic report includes an `lt1_ride_coverage` section with counts only (#2535): rides of the last 60 days with a power profile (`rides`, outdoor and indoor) and, per power variation limit 0.15, 0.20 and 0.25, how many of them have a 10 bpm band with at least 10 steady minutes within that limit (`qualifying`). It is an upper bound of the rides the LT1 power (card M9) can use and checks whether the 0.15 limit leaves outdoor rides out.
- **FIT File Inventory**: The diagnostic report includes a `fit_inventory` section that shows what the FIT files read by the Garmin and Wahoo detail fetch and the stream backfill hold beyond the mapped content, grouped by recording origin (`garmin`, `wahoo`, `zwift`) and sport: `files` read, and the number of files holding each unmapped message number (`messages`), each unread field of a mapped message as `message.field` (`unmapped_fields`) and each declared developer field as `developer_index.field` (`developer_fields`). The fields and messages the FIT mapper reads since version 10 (breathing rate, lap trigger, workout step index, lap grade-adjusted speed, `workout_step` and `zones_target`, and the workout message, whose text is never kept) are no longer listed as unmapped. `new_decodes` (#2220) counted files for these four items before the mapper read them, and goes on counting: with a breathing rate (record 20.108, lap 19.136 and 19.137) or a lap's grade-adjusted speed (19.161) inside the canonical bounds (`.in_bounds`) or outside them, zero included (`.out_of_bounds`) as `respiration_record`, `respiration_lap_avg`, `respiration_lap_max` and `lap_grade_speed`; with laps naming a workout step (`lap_step_index`), and whether all of those indexes name a workout step of the same file (`lap_step_index_resolved`) or not (`lap_step_index_dangling`); with workout steps (`workout_steps`, and `workout_steps_max`, the most steps in one file); and with the zone basis of the watch (`zones_target`). It holds numbers only: developer field names, values, ids, timestamps and positions are not kept. A file read again (the stream backfill replay) is counted once; for that, hashes of the last 5,000 files stay in the key/value store under `fit_inventory` and never appear in the report. Counting starts with the release that carries it and needs no extra download.
- **Garmin Detail Fallback**: A Garmin detail fetch whose original-file call failed or hit a rate limit falls back to Garmin's chart streams and splits. Those never replace the full-resolution streams and device laps an earlier file gave: the stored sets stay, the fetch counts as incomplete and is retried. The `garmin_detail_fallback` section counts fallback sets kept out (`kept`) and stored where nothing better was stored (`stored`); numbers only.
- **Mapper Replay Size**: The `mapper_replay` section (#2220) counts what the next detail mapper bump would download again, numbers only.
  - `garmin.records`: the Garmin activities of the last 90 days (`window_days`) whose stored detail sets the bump makes outdated, with `strength` of them needing one extra call.
  - `garmin.pending`: those the detail backfill still has to fetch for the current mapper version.
  - `garmin.passed_over`: those it no longer fetches although their full streams or device laps are still below the current mapper version. Empty marks and retries hold only for the mapper that made them, so after a bump every window activity gets one fresh fetch first. The total splits by reason:
    - `garmin.passed_over_retries`: three failed fetches on this mapper. The replay is done when `pending` and `passed_over_retries` are both 0.
    - `garmin.passed_over_empty`: marked empty on this mapper, because Garmin served no detail part. Their streams and laps came from the stream backfill (#1763), which has no replay window for Garmin, so they keep the older mapper's streams and laps. No path refreshes them; whether the Garmin stream backfill should get a replay window is decided from this count after a replay.
  - The replay budget of today (UTC): `garmin.daily_budget` and `garmin.per_refresh` replay fetches, `garmin.replayed_today`, and `garmin.clean_today` (no 429 or Garmin error yet today).
  - `garmin.issue_kinds.<field>.<reason>`: how often a Garmin detail fetch hit each mapping issue, by the mapper's field name and reason (for example `lap.out_of_range`), counts only. The warning `garmin_activity_detail_mapping_issues` carries the same `kinds`. The mapper-11 fields (breathing rate, lap grade-adjusted speed, workout steps, zone basis) raise no issues: an invalid value becomes empty.
  - `wahoo.records`: the Wahoo sessions of the last 365 days whose full streams the stream backfill would download again.
- **DFA-α1 Window Series**: Since DFA-α1 method 3 (#3273) a chest-strap recording keeps its analysed 2-minute windows (start on the beat clock, mean heart rate, alpha1, artifact share) in `activity_detail_sets.dfa_alpha1`, also without a 0.75 crossing; the RR intervals stay unstored. It came without a mapper version bump under the guard's third clause (the self-versioned additive field, approved by the athlete after a Fable review): rows of method 2 were never evaluated for the series and stay so until the next bump of the Garmin and FIT detail mappers replays them. No dedicated bump is made for it while the #2220 replay is still pending. The `dfa_series` section counts the chest-strap runs of the last 60 days by method: `with_series`, `before_series` and `without_result` (counts only).
- **Canonical Provider Composition**: The diagnostic report includes a `canonical_provider_composition` section (`status` `available`, or `unavailable` without details when a count fails). `sessions.total` counts the surviving canonical sessions and `sessions.by_providers` counts them by the providers of their active records (for example `garmin+wahoo`). `observations.unrecognized_kinds` only counts stored observation kinds outside the vocabulary. `domain_rows` counts active sleep period, zone configuration and power curve rows per provider (`local` for rows without one). The section carries counts and vocabulary identifiers only, never ids, names, dates or values.
- **Session Focus Backfill**: Once per version the canonical backfill worker runs a last stage that stores the derived session focus (and the strength intensity) on future planned units that lack it, only where the derivation is unambiguous. Past, archived and contested units stay untouched, no exercises are invented, the sync state is kept and no provider is written. The diagnostic report shows `session_focus_backfill` with `status`, `version`, `counts` (`focus`, `intensity`, `undecided`) and `undone`. The changes are recorded in the change history.
- **One-time Garmin LT2 store**: on the first start of 2.2.30 or later, the canonical backfill worker's last stage stores Garmin's LT2 values in effect once as local values (athlete, 2026-11-24, #4135). The diagnostic report shows `garmin_threshold_store` with `status` (`not_started`, `complete` or `failed`), `stored_count`, `stored_sports` (`run`, `ride`: values stored per sport) and `history_rows` (change-history rows stamped `system:#4135`); counts only, never a value. `scripts/prod_diagnostics.py --section garmin_threshold_store` prints them.
- **Retired Weekly Plan Removal**: The profile no longer has a weekly plan. A last stage of the canonical backfill worker deletes the old `weekly_plan` key from the stored profile once (state key `profile_weekly_plan_removal_state`); a database restored from an older backup runs it again, and every profile read and save ignores the field meanwhile. The diagnostic report shows `profile_weekly_plan_removal` with `status`, `version` and `removed`.
- **Retired Rating Backfill Removal**: The one-off Garmin rating backfill has finished and is gone. A stage of the canonical backfill worker deletes its leftovers once (state key `rating_backfill_removal_state`): the `garmin_rating_backfill_state` key and the `rating_history` cursor. Version 2 also deletes the retired FIT value probe's `fit_value_probe` key (counts and file hashes, #3396); a database that finished version 1 runs it once more. Stored `rating_backfill` jobs stay as job history; the queue already settles a leftover one (an interrupted run is not replayed, a queued one fails as an invalid request). A database restored from an older backup runs it again.
- **Session Rebundle**: Bundling of Garmin and Wahoo copies runs only when an ingest touches a day, so copies stored before the matching rule widened (#1954) stay separate. A stage of the canonical backfill worker links them once per version (state key `session_rebundle_state`; version 2 also deletes stored copies of sessions the athlete deleted, which undoing that delete brings back) with the regular session linking on every day holding both providers, in one transaction; hidden, provider-deleted and athlete-confirmed sessions are never touched and nothing is split. The diagnostic report shows `session_rebundle` with `status`, `version` and `counts` (`days`, `linked`); the log line `session_rebundle_completed` carries the same counts.
- **Stored Payload Sizes**: The diagnostic report includes `database.stored_payload_bytes`, the UTF-8 byte size of the stored `garmin_state`, `garmin_snapshot_legacy` (the retired snapshot a migrated database keeps) and `diagnostic_capture_entries` values (`0` when absent). SQL measures this without loading or parsing the payloads in Python; the report adds only the byte counts. This is a stored-payload measurement, not the process's RAM usage.
- **Provider Sync Times**: The diagnostic report lists `sync.providers` for Garmin, Wahoo and Intervals.icu with `last_sync_at` and `last_plan_sync_at` (timestamps or `null`).
  For Garmin and Wahoo `last_sync_at` is the last successful refresh; Intervals.icu is output only and is never read, so its `last_sync_at` is the last completed push job of any type.
  `last_plan_sync_at` is the last completed `plan_push` job of the provider.
  `plan_sync.recent_jobs` lists the recent plan-push jobs of every provider with their `provider`.
  `plan_sync.push_counts` counts, per provider, the job and item statuses (settled items included) and error classes of every plan push of the last 7 days, and of jobs still queued or running whatever their age (#2878), so one provider's failure or a stuck job stays visible however many pushes of another follow.
  `plan_sync.stuck_jobs` counts, per provider, the plan-push jobs still queued more than 2 hours after their planned start (a retry backoff does not count) or running for more than 2 hours (#2953).

- **Runtime Memory Diagnostics**: The diagnostic export adds `runtime.process_memory`: available Linux RSS, peak RSS, locked/anonymous/file memory and virtual bytes, thread count, mapping count and kernel mapping limit. Only numeric counters are exported; process memory, mapping addresses and file paths are never captured. Unavailable OS counters are omitted. Sync start, completion and failure log events include the same counters for before/after comparisons; the snapshot byte count is measured only for the diagnostic report.
- **Newest App Backup**: The diagnostic report includes a `backup` section (#2996): `known` (whether the app has made a backup), and for the newest one its age in hours, its size in bytes and `verified` (its integrity and foreign key checks passed; an unchecked snapshot is never sent). The record is written only when a backup download through the app was sent in full, with the time its snapshot was taken; backups made outside the app (host copies) are unknown to it, and a restore brings back the record stored in the restored file. No name, path or content is reported. `backup.automatic` reports the automatic copies (below): `enabled`, `nightly_count`, `newest_age_hours`, `premigration_present` and `last_failure_age_hours`. `scripts/prod_diagnostics.py --expect-backup-hours 24` fails unless such a backup or an automatic copy that recent exists, which schema releases require.
- **Automatic Backups** (#3760): The app keeps verified encrypted copies of the database without any setup: one each night from 03:30 in the athlete's time zone and one right before every schema migration. They go to `automatic-backups` inside the data directory; `BACKUP_DIR` names another directory (for example a mounted share) and `BACKUP_DIR=off` switches them off. Each copy is the backup download's snapshot, encrypted with `APP_PASSWORD`, and gets its final name only after its integrity and foreign key checks passed. The 7 newest nightly copies and the newest pre-migration copy are kept; older ones are deleted only after a newer copy is verified. A failed nightly copy is logged (`database_backup_automatic_failed`), shown in the diagnostics and retried an hour later, and never blocks the app. A failed pre-migration copy stops the startup before the migration; the database stays unchanged. Fix the directory, or set `BACKUP_DIR=off` to start without the copy. To restore a copy, upload it under Einstellungen › Datenbank wiederherstellen like a downloaded backup. The confirmed local data purge deletes the automatic copies too.
- **Storage and Runtime Health**: The diagnostic report adds `runtime.uptime_s` and `runtime.malloc_arena_max` (the allocator arena limit, the only environment value shown), `database.file_bytes`, `database.wal_bytes` and `database.data_dir_free_bytes`, and a `recovery_copies` section with the count, newest age in hours and total size of the recovery copies beside the database (#2848). Files are only measured with `stat`; no copy is opened and no file name or path is reported. The post-release check reads them with `scripts/prod_diagnostics.py --section`.
- **Garmin Strength Push**: The diagnostic report includes a `garmin_strength_push` section with counts only (#2850) over the active strength units dated today or later. `garmin` counts those with a Garmin copy (`units`), those changed since their push (`changed_since_push`, whose structure Garmin does not hold yet), and of the others their structure (`without_structure`, `one_exercise`, `several_exercises`) and whether a weight is sent (`with_kg`, warm-up sets included). `intervals` counts the units the app sent only to Intervals.icu (`units`, and `without_structure`); they reach the watch as a single step without exercises (#1802). - **All-time Curve Build**: The diagnostic report includes a `curve_build` section with the state of the background all-time session-curve build (`pending`, `building`, `ready`, `failed`), the finished `builds` and `failures`, the last build's duration (`last_build_s`), the running build's time so far (`building_s`) and the age of a failure (`failed_age_s`), all in seconds (#2852), and since the start the session curves computed, loaded from `session_curves`, stored and failed to store (`curves_computed`, `curves_loaded`, `curves_stored`, `curve_store_failures`, #2821), so a loading Analyse card can be told from a stalled or failed build. `ready` means records are held; a changed input rebuilds them on the next all-time read.
- **Stalled Server Stack Dump**: `docker kill -s USR1 pacecraft` writes the stack of every Python thread to the container log (`docker logs`) without stopping the process. The dump contains file names, line numbers and function names only, no variable values. Capture it before restarting a container whose health check times out.
- **Database Memory Budget**: Each pooled SQLCipher connection targets a 16 MiB decrypted-page cache. SQLite's cache target is not a hard process RAM limit: Python objects, query results and other native allocations use additional memory. The database file stays encrypted; `cipher_memory_security` is OFF because locking every SQLCipher allocation in memory fragmented the process into tens of thousands of mappings until allocations failed near the kernel's `vm.max_map_count`. A larger host `vm.max_map_count` can provide temporary mapping headroom but does not correct memory growth.
- **Process Memory Ceiling**: The image sets `MALLOC_ARENA_MAX=2`. The server answers each request in its own thread; with glibc's default of up to eight malloc arenas per core, RSS kept rising with uptime while in-process caches stay bounded (#2526). A synthetic soak plateaued with two arenas and kept rising without; that production growth has this cause is a hypothesis until post-release readings confirm it. Expect RSS to settle at the fresh-start reading plus roughly 100 MiB: the SQLCipher page-cache targets of the pool (one writer and up to four readers at 16 MiB, a target, not a limit; backup and restore validation open one more connection while they run) and about 20 MiB of bounded in-process caches. RSS that keeps climbing with uptime is a regression to report.
- **Garmin Metadata Reads**: Automatic sync-window selection, current Morning Body Battery, daily planning and the nutrition day and week energy summaries extract only their required snapshot fields in SQL. Unrelated Garmin collections are not decoded into Python objects for these reads; full sync/merge reads and the stored history remain intact. **Analyse**, `/api/performance` and the Coach performance and recovery sections read Garmin values only from the canonical tables and take only the small stored sync status (freshness, fetch times, read windows) from `garmin_state`.
- **Canonical Read Source**: The diagnostic report includes a `canonical_read` section that names the source serving reads (`tables`, or `pending` while nothing is served yet), the `reason`, and whether the stored check matches the current digest. Reads come from the canonical tables once the backfill has completed at least once; a content-free marker in the backfill state records that, and an existing `complete` state counts as completed. Until then, for example right after an upgrade, reads return no values, and **Analyse → Laufen**, **Analyse → Radfahren** and the Coach report that data is being prepared instead of partial values. A failed first backfill is reported and retried automatically after a delay from its last committed cursor. After the first completion a mapper-version or time-zone change re-projects the stored records in the background while reads stay on the tables, and a sync inside the running process is written to the tables as it happens. Coverage is served from the summaries persisted at ingest; before the first completion only current summaries are reported. The section reports `serving`, `reason` and `digest_current` (false while a re-projection is pending), and reports `unavailable` if its state cannot be read.
